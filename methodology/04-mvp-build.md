# MVP 构建与快速验证

## MVP 不是「最小产品」

> MVP = Minimum Viable Product
> 关键在 **Viable（可验证）**，不是 **Product（产品）**。

MVP 唯一的目标：**验证一个核心假设**。这个假设通常是"用户愿意用这个来解决问题"。

## MVP 的四种形态

| 类型 | 做法 | 适合场景 | 时间 |
|------|------|----------|------|
| **视频 MVP** | 录一个产品 Demo 视频展示核心功能 | 需要大量开发的产品 | 1-2 天 |
| **落地页 MVP** | 一个描述产品价值的单页 + 注册表单 | 验证市场需求 | 半天 |
| **人工 MVP** | 后台人工完成服务，前端看起来自动化 | AI 驱动的服务 | 1-2 天 |
| **功能 MVP** | 只做最核心的一个功能 | 功能型产品 | 1-2 周 |

## AI + 自动化产品的 MVP 策略

### 1. 从「半自动」开始

```
全自动（目标）← 半自动（MVP）← 人工（验证）
```

示例：
- 目标：AI 自动整理家庭账单
- MVP：用户拍照上传 → AI 识别 + 人工复核 → 自动分类
- 验证：用户拍摄 10 张账单，看看准确率是否可接受

### 2. 先做「点」再做「面」

```
目标：全平台消息 AI 自动回复
MVP：只做微信一个平台 + 只做「收到」「好的」两类自动回复
```

### 3. 用 Prompt 代替模型训练

```
不用：Fine-tune 一个分类模型（2周）
而用：设计一个好的 Prompt + GPT API（2小时）
```

## 验证指标

| 指标 | 说明 | 好 | 差 |
|------|------|-----|-----|
| **激活率** | 注册后完成核心动作的比例 | > 40% | < 20% |
| **留存率** | Day 7 还在用的比例 | > 30% | < 10% |
| **NPS** | 用户是否愿意推荐 | > 30 | < 0 |
| **核心功能使用率** | 用了核心功能的比例 | > 60% | < 30% |

## MVP 检查清单

发布前确认：

- [ ] 核心假设是什么？能一句话说清楚吗？
- [ ] 如果假设被否定，最少浪费了多少时间/钱？
- [ ] 目标用户是谁？能找到 10 个试用者吗？
- [ ] 最小功能集是什么？砍掉了所有不必要的功能吗？
- [ ] 怎么衡量成功？（指标 + 阈值）
- [ ] 如果失败了，学到什么？什么时候 pivot？

## 失败模式与对策

| 失败模式 | 表现 | 对策 |
|----------|------|------|
| 功能蔓延 | MVP 做了 20 个功能 | 回到一个核心功能 |
| 追求完美 | "等做好了再发布" | 有实际用户反馈最重要 |
| 找错用户 | 试用者不是目标用户 | 严格筛选前 10 个用户 |
| 忽视数据 | 凭感觉判断"用户喜欢" | 用指标说话 |
| 过早优化 | 还没验证就开始优化性能 | 能用就行，先跑通 |

## 工具栈推荐

| 场景 | 推荐工具 |
|------|----------|
| Web 原型 | Vercel + Next.js / Streamlit |
| 移动端原型 | FlutterFlow / 微信小程序 |
| AI 接口 | OpenAI API / 通义千问 / DeepSeek |
| 自动化工作流 | n8n / Make / 自写 Python 脚本 |
| 落地页 | Carrd / Framer / Notion |
| 数据分析 | Metabase / Superset / Python+Streamlit |
| 用户反馈 | Tally / Typeform / 微信群 |
